# Проверки и замеры LasTest

Команды выполняются из корня проекта.

## Обязательные команды

| Команда | Ожидаемый результат |
| --- | --- |
| `cargo fmt --all -- --check` | код отформатирован, вывода нет |
| `cargo clippy --locked --all-targets --all-features -- -D warnings` | нет предупреждений |
| `cargo test --locked --all-targets --all-features` | все unit/integration тесты зелёные |
| `cargo build --locked --release` | `target/release/lastest`, без Go |
| `./scripts/e2e.sh` | первый администратор, readiness, задача, отчёт, рестарт, WhatWeb на снимке без сети, отсутствие Go/Python/компиляторов |
| `docker compose config -q` | валидная конфигурация с настройками по умолчанию |
| `docker compose pull` | образ по digest скачан |
| `docker compose up -d --no-build` | API/worker без сборки |
| `docker compose ps` | оба сервиса запущены |
| `git diff --check` | нет whitespace errors |

Перед запуском `scripts/e2e.sh` передайте образ по digest в `LASTEST_IMAGE`. Скрипт создаёт собственные контейнеры, сеть и том. Для независимой проверки Compose используйте отдельный локальный порт и тестовый том.

## Фактические замеры

Среда: macOS Darwin x86_64, Intel Core i7-9750H (2.60 GHz), 16 GiB RAM, Rust 1.100.0, release build, локальный стенд `127.0.0.1`, один worker, `max_concurrent_jobs=1`.

На этапе перехода прошли `cargo fmt --check`, `cargo clippy ... -D warnings`, `cargo test --locked --all-targets --all-features`, `cargo build --locked --release`, проверка конфигурации Compose и `git diff --check`.

| Показатель | Значение | Условия |
| --- | --- | --- |
| Размер binary | 10.7 MiB (11 215 664 байта) | `target/release/lastest`, `strip`, LTO thin |
| Время до readiness | 0.215 s | пустая БД, запрос readiness |
| Память API в простое | ~5.7 MiB RSS | после readiness, без запросов |
| Память worker в простое | ~4.9 MiB RSS | очередь пуста |
| Суммарная память | ~10.6 MiB RSS | API + worker |
| DNS `dns.records` | 500 хостов / 1.58 s ≈ 317 хостов/с | локальный UDP DNS, только A, один worker, динамическая проверка scope |
| HTTP `http.probe` | 500 URL / 2.64 s ≈ 189 запросов/с | локальный HTTP-сервер, один worker, динамическая проверка scope на каждый запрос |

Ориентиры архитектуры — до 100 MiB сжатого образа и до 120 MiB памяти в простое. При отдельной проверке на Linux `amd64` образ собрался, Compose запустил API и worker по digest с `--no-build`. Размер сжатых слоёв и конфигурации в тестовом реестре составил 37 027 309 байт (35,3 MiB). Сквозной тест прошёл все девять шагов после исправления передачи stdin, имени API в сети Docker и записи правил scope в `/tmp`. Для повторной проверки можно использовать следующие команды.

```bash
docker build -t lastest:local .
docker image inspect lastest:local --format '{{.Size}}'
docker save lastest:local | gzip -9 | wc -c
```

Сравнение с 1.x на тех же фикстурах не выполнено: работоспособная база 1.x с Kali/Go-инструментами в этой среде отсутствовала. Ускорение не заявляется; сетевые задачи ограничены сетью/квотами провайдеров.

## Ручной чек-лист UI

1. На пустом томе открыть `/`, получить код командой `docker compose exec api lastest admin setup-code` и создать администратора через форму. Войти и проверить, что панель появилась сразу в видимой области. Обновить страницу и убедиться, что с действующей сессией сразу открывается панель.
2. Убедиться, что проект не выбран и dashboard не показывает mock-метрики.
3. Создать проект, добавить и утвердить scope.
4. Запустить `http.probe` на локальном стенде, увидеть partial/empty состояния.
5. В Scans выбрать Asset Discovery, настроить источники, проверить read-only состояние Censys без поля ключа, включить/выключить активный HTTP и выбрать карточку и нажать общую кнопку Start scanning. Убедиться, что создаётся одна цепочка из трёх стадий, а не три параллельных задания.
6. В Assets проверить фильтры кандидатов (источник, DNS, совпадение IP, текущий Scope, confidence, interest), различие `not_permitted` и `no_addresses`, карточку кандидата, карточку актива и «Add to Scope» без потери несохранённых правок и без автоматического утверждения Scope.
7. Проверить Assets/Findings/Reports; скачать JSON, CSV и отдельные `discovery-json`/`discovery-csv`.
6. Пройти все действия только клавиатурой (Tab/Shift+Tab/Enter/Space), проверить видимый focus.
7. Войти viewer: действия изменения скрыты/запрещены, Users недоступны.
8. Войти через HTTPS reverse proxy: cookie содержит `Secure`, `HttpOnly`, `SameSite=Strict`; запрос с чужим `Origin` отклонён.

## Проверка производительности UI

1. На пустом и заполненном проектах открыть Dashboard с чистой вкладки браузера. В Network проверить, что стартовый запрос Dashboard не ждёт `/api/task-types`. При обычной повторной загрузке браузер может получить `304` для неизменённых JS, CSS и шрифта.
2. Перейти из Dashboard в Hosts, Candidates и URLs. Сравнить Network и Performance при первом открытии и при возврате на уже загруженную вкладку в пределах 30 секунд. Hosts и URLs используют свои запросы без загрузки Dashboard. При возврате с актуальными данными таблица видна сразу, без запроса и повторного построения строк. Повторить для Users.
3. Замедлить ответы API, дважды нажать Refresh, изменить фильтр и переключить проект до получения ответа. Проверить, что одинаковый запрос выполняется один раз, показанные строки остаются во время обновления, а результаты предыдущего поиска и проекта не появляются в новом.
4. В Scans раскрыть детали завершённого задания и дождаться обновления соседнего активного задания. Раскрытая карточка сохраняется. При активном задании проверка статуса выполняется с интервалом 5 секунд после ответа, в простое — через 30 секунд. После ухода с Dashboard и Scans опрос прекращается.

## Очередь и большие DNS-словари (22 ноября 2026)

Регрессии `equal_timestamp_jobs_are_claimed_in_submission_order` и
`racing_workers_claim_each_job_once` проверяют порядок готовых заданий с одинаковой
секундой создания и одновременный захват 24 заданий четырьмя worker без повторов.
`worker_parallel` проверяет 1/4 слота, пополнение, изоляцию ошибки/отмены, порядок
цепочки и остановку активных процессов. Тест подготовки 50 000 слов на однопоточном
Tokio подтверждает, что отмена и отзыв Scope обрабатываются до запуска dnsmap.

Подготовка 50 000 уникальных префиксов в debug build на macOS x86_64 заняла
100,608 s до изменения и 1,718 s после. Вместо сетевого dnsmap использовался
исполняемый stub `#!/bin/sh\nexit 0\n`, `concurrency=8`; измерялся только вызов
`dnsmap::discover` с одним разрешённым деревом Scope. Это замер подготовки и
процессного адаптера без DNS, не оценка ускорения полного сканирования. Чтение Scope
из SQLite на каждом слове заменено проверкой в памяти с периодическим чтением
текущего Scope, уступкой runtime и обязательной проверкой перед запуском процессов.

Сравнение бинарников на отдельной внутренней Docker-сети (без внешнего DNS):
5000 имён `wN.bench.test`, задержка UDP-фикстуры 5 ms, 50 положительных ответов
(A-only, AAAA-only и A+AAAA), остальные NXDOMAIN с SOA. Медиана трёх последовательных
запусков при остановленной фоновой сборке, включая запуск контейнера:

| Инструмент | Параллельность | Время |
| --- | --- | --- |
| dnsmap 0.36 с патчем LasTest | 8 процессов | 14,495 s |
| dnsx 1.3.1 | 8 потоков | 16,682 s |
| dnsx 1.3.1 | 100 потоков | 3,321 s |

Все запуски вернули ровно ожидаемые 50 имён, включая AAAA-only. dnsmap использовал
системный resolver Docker, dnsx — тот же локальный DNS напрямую (`-r IP:53`),
`-a -aaaa -j -omit-raw -duc -silent`. Сравнивалось только обнаружение по заранее
подготовленному списку: служебные пробы dnsmap отключены патчем, `-auto-wildcard`
у dnsx не включён; фильтрация wildcard и публикация Assets LasTest сюда не входят.
Это синтетический замер, а не прогноз времени для 50 000 публичных имён.
При равной параллельности преимущества замены не получено; ускорение dnsx связано
с 100 одновременно обрабатываемыми именами. В текущей версии остаётся dnsmap.
[dnsx](https://github.com/projectdiscovery/dnsx) поддерживает явный resolver, A/AAAA,
JSONL, ограничение потоков и RPS. [puredns](https://github.com/d3mondev/puredns)
требует massdns и настройки resolver/доверенной перепроверки; его скорость здесь
не измерялась. Любой новый адаптер должен сохранить правила Scope, отзыв допуска,
отмену, wildcard и обязательную A/AAAA-проверку перед Assets.

После добавления вариантов 10/20/50/100 повторён тот же локальный DNS-стенд
с реальным dnsmap из итогового образа. Медианы трёх запусков для 5000 слов:

| Процессы dnsmap | Время |
| --- | --- |
| 10 | 10,998 s |
| 20 | 5,813 s |
| 50 | 3,834 s |
| 100 | 3,654 s |

Все 12 запусков вернули ровно 50 ожидаемых имён, включая AAAA-only.
Интеграционный тест адаптера на барьере подтверждает пик 10/20/50/100 одновременно
запущенных исполнителей, разделение списка без дублей и исключение запрещённого
имени до запуска. API-каталог предлагает только эти четыре значения с default 20;
новые задания со старыми значениями отклоняются, уже сохранённые задания с 4/8/16
продолжают выполняться. Общий лимит заданий worker остаётся отдельной настройкой.

Итоговая проверка: `cargo fmt --all -- --check`, Clippy со всеми target/features
и `-D warnings`, полный набор 121 теста, `node --check ui/app.js` и синтаксис E2E
скрипта прошли. Release-образ проверен через `scripts/e2e.sh` по локальному digest:
HTTP, dnsmap, JSON-артефакт через API, сохранение истории после рестарта, новый
каталог 10/20/50/100 с default 20, таймаут 7200 и непривилегированный runtime.
Отдельный Compose pull/up без сборки подтвердил env override 1234 секунд у API
и worker, четыре слота заданий и отказ запуска при нуле/нечисловом таймауте.
Все стенды использовали отдельные временные БД, тома и локальные цели.

## dnsx: нагрузка, порядок и частичные результаты (24 ноября 2026)

Текущий `dns.wordlist` использует один dnsx 1.3.1 и локальный UDP/TCP-транспорт с
общим ограничителем исходящих запросов. Старые замеры dnsmap выше относятся к
предыдущей реализации. По умолчанию выбраны 8 параллельных имён и 50 DNS-запросов/с;
в Scans доступны настройки частоты, параллельности и Dedicated/System DNS. Настройка
System учитывает `LASTEST_DNS_SERVER`, затем системный DNS. Dedicated не использует
скрытый fallback на системный DNS. Кэшируются только успешные/отрицательные ответы
с действующим TTL; ошибки транспорта не превращаются в NXDOMAIN.

`tests/wordlist_dnsx.rs` проверяет приоритет обычных заданий, захват четырьмя worker
без второго перебора, файловую блокировку пережившего lease процесса, общий таймаут
включая wildcard, ограничение UDP-пакетов, IPv4/IPv6, потери с успешным повтором,
независимость обычного DNS, System override, отзыв Scope без последующих запросов,
отмену с обычным 60-секундным lease и сохранёнными Assets/JSON, скачивание checkpoint
после аварии/истечения lease и отказ устаревшим записям. Проверены отмена подготовки
50 000 слов и список, целиком исключённый Scope, без DNS-трафика. Управление отменой
опрашивается каждые 500 ms отдельно от heartbeat; прогресс сохраняется примерно раз
в секунду и перед финализацией.

Сквозной нагрузочный сценарий выполнен на внутренней Docker-сети с двумя worker,
отдельным рекурсивным DNS-стендом и обычным DNS для остальных модулей. Ответы задержаны
на 30 ms; первый A-пакет каждого 97-го имени теряется. Эталон содержит A-only,
AAAA-only, dual-stack и отрицательные ответы. Отдельно проверены CNAME и UDP → TCP.

Проверены скачивание JSON через браузер во время работы, результат через API,
финальный артефакт и экспорт отчёта. В интерфейсе подтверждены частота 50/100,
Dedicated/System DNS и параллельность 4/8/16; скриншот и данные стенда хранятся вне Git.
Это локальная проверка устойчивости/полноты, а не гарантия времени для внешнего домена.

E2E использует отдельный pinned Python-контейнер только как DNS-фикстуру на внутренней
сети. API получает отдельную сеть для локального опубликованного порта; worker и DNS
не имеют внешней сети. В runtime LasTest Python/Go toolchain отсутствуют, dnsmap не
установлен, dnsx и offline WhatWeb доступны. Итоговый image проверяется по digest.
Compose проверяет единые env overrides API/worker, default с учётом потолка частоты,
приоритет нового имени таймаута над legacy и отказ при неверных значениях/metadata DNS.

использовали только временные проекты/БД/тома и локальные DNS/HTTP-фикстуры.
